Slack 수신기

Bun에서 Slack 공식 @slack/socket-mode가 앱 토큰으로 WebSocket 연결을 연다. 아인은 봇 토큰의 워크스페이스·사용자 ID와 소켓 연결의 앱 ID를 확인한 뒤 이벤트를 받는다. 수신 대상은 봇이 받은 DM, 감시 채널의 멘션, 참여한 스레드의 답글, 봇 게시물에 달린 반응이다.

  1. Socket 이벤트
  2. 필터·본문 마스킹
  3. SQLite 커밋
  4. Slack ACK

같은 메시지가 멘션과 답글로 두 번 도착해도 채널과 메시지 시각으로 중복을 걸러낸다. 봇 자신의 글은 참여한 스레드를 기록하는 데 쓰인다. 차단한 사용자의 메시지는 작업 큐에 들어가지 않는다.

listen은 stdout에 한 이벤트당 INBOUND 한 줄을 쓴다. orchestrate는 처리할 메시지의 수신 키와 작업을 같은 트랜잭션에 보존한다. 커밋이 끝나야 아인이 SDK의 ack()로 접수를 확인한다. 반응과 REPLY=no는 새 작업을 만들지 않는다.

연결이 끊기거나 Slack이 연결 교체를 요청하면 아인이 새 SDK 클라이언트를 시작한다. 앱 ID를 확인한 뒤 SQLite의 마지막 복구 위치부터 Slack Web API로 알려진 채널과 스레드를 조회한다. 연결 중에 받은 이벤트와 기록 조회 결과가 겹쳐도 같은 중복 키를 사용한다. 기록 조회와 답변 게시는 봇 토큰을 쓰는 HTTP 호출이다.

Slack 앱의 봇과 Agent 기능

예제 매니페스트로 설치하면 아인은 봇 사용자로 DM과 채널에 답한다. Slack Agent 화면을 활성화한 앱도 같은 Socket Mode로 이벤트를 받는다. Agent 화면에서 보낸 일반 DM은 기존 메시지 처리 경로를 쓸 수 있다. 사용자가 보고 있는 채널 읽기, Slack 세션의 진행 상태 표시, 중지 버튼을 통한 작업 취소는 각각 이벤트 처리와 Web API 연동이 필요한 추가 기능이다. 현재 아인은 일반 메시지 수신과 스레드 답글을 지원한다. Slack Agent 개발 가이드

오케스트레이터

bun run ein orchestrate로 시작하는 TypeScript 코드다. 대화의 순서를 관리하고, 설정으로 결정할 수 있는 프로젝트를 선택하고, herdr를 통해 세션을 열거나 재개한다. 한 대화에서는 SQLite에 들어온 순서대로 처리한다. 여러 대화의 담당·프로젝트 세션이 동시에 수행하는 작업은 최대 세 건이며, 메인 판단은 별도 한 건씩 처리한다. 완료된 세션은 후속 요청에 재사용한다. 같은 프로젝트를 선택한 세션은 등록된 작업 디렉터리를 공유한다.

작업 위치를 정하는 기준

  • 대화는 워크스페이스와 채널, 스레드 원글 시각으로 구분한다. 최상위 1:1 DM은 DM 채널로 묶고 명시적 DM 스레드는 별도로 다룬다.
  • 새 대화에 project:ein이 있거나 전용 채널이 한 프로젝트를 가리키면, 코드가 projects.ein.path를 작업 위치로 선택한다. 단서가 충돌하거나 미등록 경로를 받으면 전용 메인에게 묻는다.
  • 기존 대화는 처음 기록한 담당 세션을 사용한다. 두 번째 프로젝트 작업은 같은 대화 아래 별도 작업 세션에서 실행하고 담당 세션이 결과를 받아 답한다.

세션과 답변의 소유권

새 세션은 모두 최상위 runner를 쓴다. 아인은 논리 세션 ID, 작업 디렉터리, 실행기를 먼저 기록한다. herdr pane은 현재 터미널을 가리키고, 실행기 고유 세션 ID는 그 터미널이 사라진 뒤에도 원래 대화 문맥을 찾는 데 쓰인다.

발신 목적지는 수신한 이벤트에서 가져온다. 최종 답변이나 확인 질문을 SQLite에 먼저 넣고, 발신기가 chat.postMessage에 전달한다. 스레드에는 원글 시각을 넣고 일반 DM에는 최상위로 게시한다. 성공하면 Slack이 돌려준 메시지 시각을 기록한다.

메인 세션

처음 판단이 필요할 때 아인이 중립 작업 디렉터리에서 전용 에이전트를 열고 이후 판단에 재사용한다. 등록 프로젝트가 있는 설치에서 새 대화에 대상 단서가 없으면 일반 질문도 먼저 메인으로 간다. 전용 메인은 한 번에 한 요청을 처리한다. 메인이 프로젝트를 고르거나 사용자의 답을 기다리는 동안 다른 대화의 작업 세션은 계속 실행할 수 있다.

입력에는 원문, 해당 대화의 관련 문맥, 등록된 프로젝트 ID와 전용 채널 정보가 들어간다. 에이전트의 출력은 작업 ID와 시도 번호에 묶인 로컬 결과 파일이다. 아인이 결과 형식과 현재 시도, 등록된 프로젝트를 확인한 뒤 다음 단계로 이동한다.

  • assign은 등록된 프로젝트 ID를 돌려준다. 코드가 설정에서 경로를 찾는다.
  • ask는 원래 대화에 질문을 게시한다. 질문이 게시된 Slack 시각을 확인한 뒤, 그보다 늦게 같은 대화에서 같은 요청자가 보낸 답을 기존 작업에 연결한다.
  • reply는 답변을 내놓는다. 메인이 새 대화의 일반 질문에 바로 답하면 중립 담당 세션을 예약한다. 같은 대화의 다음 요청은 이 담당에게 간다.

담당 세션은 우선순위 충돌이나 승인이 필요하면 escalate와 사유를 돌려줄 수 있다. 메인이 이 건을 검토하고, 필요한 경우 원래 대화에 질문한다. 메인의 결정은 담당에게 돌아간다.

에이전트 작업과 확인 응답은 소유자에게만 허용한다. 다른 사용자의 수신 이벤트가 응답 대상으로 선정되면 아인이 고정된 안내문을 보낸다. 해당 사용자의 본문은 이후 에이전트에게 전달할 문맥에서도 제외한다.

재시작과 보류

listen은 stdout 전달을 마치면 수신 레코드의 본문을 비우고 중복 키를 남긴다. orchestrate는 다음 대화에 필요한 요청·답변 이력을 SQLite stateFile에 보존한다. 토큰 패턴을 가린 뒤에도 대화 내용은 남는다.

<stateFile>.orchestration/<설치 UUID>/ 아래에는 중립 작업 디렉터리(workspaces/), 실행기 상태(sessions/), 시도별 예약과 결과(turns/)가 있다. 설치 ID는 같은 DB를 재시작할 때 유지된다. 운영자는 DB와 이 디렉터리의 접근을 관리하고, 백업·복원할 때 둘을 함께 보존한다.

수신 저장 직후 종료
SQLite에 저장한 작업부터 이어간다. Slack이 같은 메시지를 다시 보내도 고유 키로 작업 추가를 막는다. 연결 공백 중 처음 생긴 미등록 DM이나 이모지 이력은 완전히 복원할 수 없다.
세션 실행 중 종료
실행기 입력을 보내기 전 시도를 예약한다. 재시작하면 같은 예약의 결과 파일을 기다리고, 작업 ID와 시도 번호가 맞아야 결과를 받는다. 결과 대기 기한은 30분이다. 입력 전달 여부나 세션 정체를 확정할 수 없으면 작업을 보류한다. 같은 대화의 뒤 작업은 기다리고 다른 대화의 처리는 이어진다.
Slack 응답 유실 또는 제한
429를 받으면 Slack의 Retry-After 이후 재시도한다. 전송 도중 끊겼다면 원래 스레드의 답글 또는 DM 기록에서 봇 작성자와 메시지 메타데이터의 전송 식별자를 대조한다. 확인되면 전송 완료로 기록하고 확인하기 어려우면 보류한다. 보류된 답변 뒤의 같은 목적지 발신은 기다린다.

보류 상태 확인

운영자가 아인을 정상 종료한 뒤 아래 읽기 전용 쿼리를 실행한다. 예시는 기본 DB 경로다. 출력은 작업 번호와 상태, 사유로 한정한다.

sqlite3 -readonly ~/.local/state/ein/inbound.sqlite \
  "SELECT id, stage, attempt, reason FROM jobs WHERE status='held';"
sqlite3 -readonly ~/.local/state/ein/inbound.sqlite \
  "SELECT seq, status, reason FROM slack_deliveries WHERE status IN ('uncertain','held');"

작업 보류는 실제 pane과 실행기 세션, 해당 시도의 결과 파일을 확인한다. 발신 보류는 원래 Slack 스레드에서 메시지 게시 여부, 봇의 채널 접근과 기록 조회 권한을 확인한다. 보류 건의 수동 해제 명령은 제공하지 않는다.

검증 범위

오프라인 테스트는 임시 SQLite와 Slack·실행기 대역으로 메시지 중복, 대화별 순서, 프로젝트 선택·확인 대기, 전송 재시도와 재시작 경계를 검사한다. 별도 동시성 검사에서 전용 채널의 스레드 16개에 각각 8건을 넣었을 때, 응답 128건이 발신 대기열에 들어갔다. 메인 호출은 0회, 동시 작업은 최대 3개였고 같은 스레드에서 순서가 바뀐 건은 없었다.

Bun에서 Slack 수신 연결 검증

실제 Ein CLI와 SDK를 로컬 WSS·HTTPS 서버에 연결해 여섯 가지 시나리오를 검증했다. 이 테스트는 임시 TLS 인증서 생성에 openssl을 사용한다. 서버가 ACK를 받자마자 CLI를 종료한 뒤 DB를 다시 열어 수신 키와 작업이 남아 있는 것을 확인했다. 작업 저장을 실패시키자 수신 키가 롤백되고 ACK가 발생하지 않았다.

Bun 1.4.2와 SDK 3.2.0으로 연결을 끊은 동안 기록 조회에만 추가한 DM 한 건을 복구했다. 이어 같은 이벤트를 소켓으로 재전송하고 연결도 교체했을 때 stdout에는 한 번만 출력됐다. 유휴 연결에서 35초 동안 ping 일곱 번과 pong 응답을 주고받으며 SQLite 복구 위치가 전진했다. 다른 앱 ID로 연결했을 때는 이벤트 처리와 ACK가 발생하지 않았다.

Agent 화면에서 보낸 메시지 형식을 재현한 테스트에서는 DM 스레드 작업 한 건이 저장됐다. 같은 대화에 보낸 agent_session_stopped는 ACK 후 무시됐다. 이 검증은 로컬 서버에서 실행했다. 실제 Slack 워크스페이스에 Agent를 설치하거나 중지 버튼을 누르는 UI 검사는 별도다. Bun 소켓 통합 테스트

실제 실행기의 결과 파일 작성

제품의 createRunTurn이 실제 herdr를 거쳐 OMO와 Codex에 각각 한 건을 전달했다. 모델 응답은 로컬 테스트 서버에서 반환했다. OMO는 RPC로 요청을 받고 내장 write 도구로 결과 JSON을 최종 경로에 직접 썼다. Codex는 허용된 결과 디렉터리에 임시 JSON을 쓰고 최종 파일명으로 원자적으로 변경했다. 두 경우 모두 아인이 작업 번호와 시도를 대조해 예상한 reply를 회수했다.
