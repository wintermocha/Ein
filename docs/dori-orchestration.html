herdr에서는 먼저 agent prompt를 시도한다. agent_not_ready가 돌아오면 전경 에이전트를 다시 확인하고 본문 입력과 Enter로 대체할 수 있다. 이 경로에서는 본문 개행이 / 로 바뀐다. 본문이 입력된 상태에서 Enter만 실패했다면 harness는 같은 에이전트에 Enter만 재시도한다. 본문 자체가 도착했는지 모호하면 HELD로 보관하고, 리드가 pane을 읽은 뒤 도착했으면 inbox ack, 빠졌으면 inbox resend를 선택한다. 둘 다 전송을 복구하는 동작이다. 작업 품질을 고치라는 요청은 새 지시 메시지로 작성한다. herdr의 전송 방식 Enter 재시도 HELD 통지

결과 판정

“끝났습니다”를 들은 뒤 무엇을 확인하나

같은 저장소 안에서도 진입점에 따라 종료 계약이 다르다. 루트 CLI에서 작업 세션은 최종 답과 증거를 리드에게 인계한다. dori-mode에서는 리드가 위임할 때 쓴 Done = 조건을 감시기가 다시 실행할 수 있다.

경로와 신호판정 주체와 근거다음 동작
루트 · ready작업 세션이 비어 있지 않은 최종 답과 증거 항목 1개 이상을 제출한다. CLI는 필드의 존재를 확인하며 증거 내용 해석은 리드에게 맡긴다.ready로 보관하고 리드에게 알린다. 리드가 done을 호출하면 런타임을 조회해 working / blocked / error는 거절한다. 이미 사라진 pane은 닫기를 생략하고 작업을 done으로 기록한다. ready와 done
루트 · gone감시 대상인 working / waiting lane의 pane이 사라졌다. duty는 조회하는 동안 READY나 마이그레이션이 발생했는지 레코드를 다시 읽는다.아직 감시 대상이면 lost로 저장하고 리드에게 알린다. 종료 신호를 받기 전 세션을 잃은 경우다. 유실 판정
Mode · report --kind done작업 세션이 자신의 진행 저널에 완료를 보고한다. 일반적인 working lane에서는 이 보고를 읽은 freshness가 진행 독촉을 멈춘다.레지스트리에서 이의제기 기한을 시작하려면 별도로 claim-done을 호출한다. 보고 상태 완료 주장
Mode · done-claimed작업 세션이 --evidence를 제출하면 주장 시각과 근거가 남는다. 리드는 실제 결과를 확인해 직접 닫거나 사유를 붙여 이의를 제기할 수 있다.작업 세션은 대기한다. watch가 30초마다 확인하고, 기본 5분이 지난 뒤에도 주장이 유효하면 자동 검증을 진행한다. 인계 규칙 watch 주기
Mode · 검증 실패 또는 이의감시기는 작업 경로의 미커밋 추적 파일, 어느 원격 추적 브랜치에도 없는 커밋, 통과하지 못한 완료 신호를 찾는다. 리드도 object-done --reason으로 별도 사유를 줄 수 있다.not-done을 기록하고 같은 pane에 사유와 수정 후 재청구 지시를 보낸다. 수정 후 새 주장을 내면 유예가 다시 시작된다. 이 경로에는 고정된 반려 횟수 상한이 없다. 이의 전달 자동 판정
Mode · 전부 통과감시기가 verified-done을 기록한다. 닫기 함수에서 완료 신호를 한 번 더 읽으므로 그 사이 결과가 달라지면 다시 이의로 돌린다.설정된 스레드 훅, 탭이나 pane 닫기, 전용 worktree 제거를 시도한다. closed 레코드의 receipt에 검사·메모·정리 결과가 남는다. 닫기와 영수증 재검사

완료 조건에는 직접 관찰할 결과를 쓴다

리드가 일반 문장으로 목적을 설명하더라도 Mode의 --done은 파서가 읽을 수 있어야 한다. merged는 PR의 MERGED 상태와 merge SHA, closed는 이슈 상태, published는 npm 버전을 조회한다. command는 종료 코드와 선택적 stdout 패턴, file은 존재와 선택적 SHA-256·JSON 필드, url은 GET 응답 코드와 선택적 본문 패턴을 확인한다. 여러 조건은 세미콜론으로 연결하며 모두 통과해야 한다. 위임 시 문법 검사 여섯 검사기

Done = command ["bun","test"]; file "summary.json" json:.accepted=3

위 예시에서 테스트가 통과해도 파일의 accepted가 2라면 검증은 실패한다. 작업자가 낸 증거는 리드가 검토할 단서이고, 감시기는 명령을 실행하고 파일을 다시 읽어 결론을 낸다. file "summary.json"만 쓰면 검사 범위도 파일의 존재까지다.

직접 닫기, PR 검증, 정리 실패의 처리 범위

직접 닫기. 리드의 close는 곧바로 closeLane을 호출해 완료 신호를 검사한다. 미푸시 검사와 5분 대기는 감시기의 자동 경로에 있다. 미푸시 검사도 전용 worktree를 우선하고 없으면 lane의 Git 작업 디렉터리를 확인하며, 추적되지 않은 새 파일은 검사에서 제외한다. 정리 도중 탭이 남거나 worktree 제거가 실패해도 그 결과를 영수증에 담아 closed로 기록할 수 있다. 수동 close 미푸시 범위 정리 결과

PR 작업. 위임 프롬프트는 작업 세션에 완료 청구 전 verify-pr 실행을 지시한다. 이 명령은 커밋 이메일을 확인한다. 소스 파일을 바꾸는 fix: 계열 커밋에 자체 테스트 변경이 없으면 경고하고, 그런 수정이 있는 PR 전체에 테스트 변경이 없으면 본문의 명시적인 No test: 사유가 필요하다. 검사 중 HEAD·본문·커밋 수가 바뀌면 실패한다. UI 반복 테스트 후보와 실행 명령을 출력하며 실행은 작업 세션의 몫이다. verify-pr 자체는 모든 lane의 close 단계에 일괄 내장된 검사가 아니다. 작업자 지침 PR 규칙 결과 형식

새 lane이 제대로 시작되었는지 확인하는 법

launch는 pane 생성 후 에이전트 시작 전에 레지스트리를 기록한다. 기본 설정에서 20초 뒤 첫 화면을 보고, 필요하면 10초씩 최대 대기 시간(기본 180초)까지 상태와 활성 goal을 재확인한다. 시작 실패를 조사할 때는 이 기록과 실제 pane을 함께 본다. 등록·시작·첫 조회

STARTUP_OK는 에이전트가 준비되고 필요한 goal이 보였다는 뜻이다. STARTUP_NO_GOAL이면 기존 lane에 목표 설정을 요청하고, STARTUP_UNCONFIRMED면 먼저 pane을 읽는다. STARTUP_ERROR는 시작 명령이나 화면에서 확인된 오류다. 원인과 기존 세션을 확인해 재실행을 결정한다. 너무 빨리 종료되어 이미 종료 기록이나 완료 보고가 남은 경우의 STARTUP_DONE은 시작 확인의 특례다. 납품 검증은 별도의 완료 경로를 따른다. 운영 지침 대기 분기 빠른 종료 판독

응답이 끊겼을 때 무엇을 다시 요청하나

Mode에서 관찰한 상황감독 동작
작업 중이고 보고가 뜸함working 상태에서 기본 15분 뒤 현재 무응답 구간에 한 번, “직전 보고 이후 끝낸 일과 다음 일”을 1~2문장으로 요청한다. 스레드가 조용한 시간은 따로 계산한다. 기본 20분 후 게시 훅이 설정되어 있으면 마지막 보고를 사용한다. 새 lane의 저널 보고는 즉시 후보가 되고, 저널 대신 읽은 기존 pane의 화면 보고는 같은 줄이 연속 두 번 보여야 한다. 이미 게시한 문장은 보류한다. 이의가 기록된 not-done은 이 독촉 대상에서 제외된다. 감시할 상태 기본값 독촉과 게시
장애·질문·정체blocker / question / halted / done 보고를 받은 저널 기반 lane에는 진행 독촉을 보내지 않는다. 컨텍스트 압축 실패, 또는 오래된 보고와 idle 프롬프트가 함께 보이면 stalled로 관찰해 독촉·게시를 보류한다. 감독기는 같은 호출 타이머가 증가하고 보고·체크포인트·파일의 진척도 기본 20분 동안 없을 때도 정체를 감지한다. 측정 가능한 예산 상한 도달은 blocker로 기록하고 리드에게 판단을 넘긴다. 화면 판독 예산과 정체
사용자가 일시정지를 요청함/goal pause가 화면에서 새로 확인되어야 paused로 기록한다. 확인되지 않으면 기존 상태와 오류 코드 3을 반환한다. 멈춘 pane이 두 번 연속 일하는 모습은 경보 사유다. 재개는 명시적인 resume으로 처리한다. 정지 확인 재개 조건
pane이 사라지거나 종료 흔적이 보임sync는 레지스트리와 실제 세션 목록을 대조해 사라진 pane·바뀐 세션을 보고한다. dead-panes는 살아 있는 런타임 상태를 우선하고, 종료 표식이 있는 같은 화면 꼬리를 두 번 확인해야 DEAD_PANE을 낸다. Mode에서 이 관찰만으로 lane이 성공·실패로 종결되지는 않는다. 세션 대조 종료 감지

운영 화면에서 not-done은 수정할 사유가 있는 열린 작업, blocked는 저널상의 대기, stalled는 진척 관찰 결과다. Mode의 lane 레지스트리에는 failed나 abandoned라는 종결 상태가 없다. 레지스트리 상태 진행 상태

프롬프트 설계

작업을 시작할 때와 다시 요청할 때, 무엇을 알려주는가

처음 위임할 때는 리드가 목표와 완료 조건을 정한다. 실행 중에 다시 보내는 지시는 상황에 따라 달라진다. 침묵이 길어지면 상태를 묻고, 검사가 실패하면 실패한 조건을 돌려주며, 다른 세션의 도움이 필요하면 누가 무엇을 해줘야 하는지 보고한다.

역할 지침과 작업 지시는 어디에 들어가나

경로세션이 받는 내용작성자와 조정 지점
하네스 · 리드와 당직up이 역할별 파일을 렌더링해 --append-system-prompt로 넘긴다. 리드는 사용자 대화·결과 검수·병합을, 당직은 대기 사유 해소와 리드 호출을 맡는다.prompts/lead.md와 duty.md가 역할을 정한다. DORI_PROMPTS_DIR로 템플릿 디렉터리를 바꿀 수 있다. 역할 주입 템플릿 선택 당직 역할
하네스 · 작업 세션start가 리드의 brief 사본 끝에 lane key와 CLI 경로를 치환한 footer를 붙인다. 새 세션의 첫 메시지는 그 파일의 경로와 자신의 key를 알려준다.리드는 목표·입력·산출물·종료 조건·제약을 쓴다. 공통 footer는 목표 설정, 증거 보고, 대기 표현, ready 제출, 리드의 종료 책임을 지정한다. 위임 지침 첫 메시지 조립 작업자 지침
dori-mode · 작업 세션launch가 선별한 교훈 → 리드의 brief → lane별 footer 순으로 입력 파일을 갱신한다. 시작 메시지는 설정의 launchKeywords, 읽을 경로, lane key, footer에 따라 보고하라는 지시로 구성한다.리드는 코드 위치, 기존 증거, 사용자가 기대하는 결과, 변경 범위를 쓴다. CLI는 thread·Done·보고 대상 pane·체크포인트·예산·완료 신청 방법을 채운다. launch --dry-run은 조립된 파일 내용을 미리 보여준다. 구성 순서 시작 문구 footer 항목 미리보기

같은 작업에 세 가지 요청을 보내는 예

아래는 dori-mode의 메시지 규약을 적용해 새로 쓴 weekly-export 예시다. 경로와 관측값은 가상이며, 마지막 두 항목은 각각 다른 상황에서 보내는 메시지다.

첫 위임 · 리드가 쓰는 brief

주간 내보내기를 사용하는 팀이 새 포맷을 읽을 수 있게 해줘.
기존 출력 out/weekly.json의 schemaVersion은 숫자 1이다.
내보내기 생성기와 해당 테스트를 수정하고 기존 rows의 의미와 순서를 유지해.
생성기를 다시 실행한 결과 파일과 회귀 테스트 결과를 보고해.

Done = file out/weekly.json json:.schemaVersion=2

--done으로 넘긴 조건은 footer에도 들어간다. 위 검사로 확인하는 것은 JSON 필드의 숫자값이다. 행의 의미와 순서까지 검증하려면 테스트를 command 조건에 추가하거나 리드가 결과를 직접 대조해야 한다. brief와 완료 조건

검수 후 수정 요청 · 리드가 관측값을 사유로 넣는다

[LEAD] not done: out/weekly.json의 schemaVersion이 문자열 "2"다. 생성기에서 숫자 2로 기록하고 산출물을 다시 생성해 줘. 숫자형 회귀 테스트도 확인해 줘; keep working, claim again when fixed

object-done --reason에 리드가 이 사유를 쓰면 CLI가 고정된 앞뒤 문구를 붙인다. watcher가 포착한 실패라면 같은 위치에 실패한 신호와 실제 점검 결과가 들어간다. 수정 후 작업 세션이 새 증거로 다시 신청한다. 이의 문구 검사 결과 전달 값·타입 확인

외부 입력이 없어 진행이 막혔을 때 · 작업 세션이 리드에게 보고한다

[REPORT] weekly-export | blocker | 내보내기 검증에 필요한 기준 데이터 파일을 읽을 권한이 없습니다. 리드가 읽을 수 있는 사본 경로를 알려 주세요.

작업 세션은 report --kind blocker --text …로 기록하고 출력 줄을 리드에게 보낸다. 리드는 경로를 찾아 알려주거나 소유자에게 필요한 조치를 요청한다. 일정 시간 소식이 없는 세션에 보내는 freshness 알림은 마지막 보고 이후 한 일과 다음 일을 한두 문장으로 요청한다. 보고 방식 리드의 대응 진행 확인 문구

다음 요청에 무엇을 남기는가

같은 lane의 재개에는 체크포인트를 쓴다. 완료한 단계마다 고유한 단계명·결과·증거·외부 작업 영수증을 적는다. 같은 단계와 같은 내용은 기존 기록을 반환한다. 재개 시 footer는 기록부터 읽도록 지시한다. 원격 작업 직후 저장 전에 중단된 경우에는 원격 상태를 먼저 확인해야 한다. 기록 검사 재개 지침

별도 세션에서 받은 판정은 PR 커밋에 묶인다

  1. 리뷰 요청. 현재 PR의 head SHA를 읽고 PR 번호·저장소·SHA를 review.md에 채운다. 기본 호출은 omo -p --no-session으로, 리뷰어에게 해당 변경의 목표, 회귀, 테스트 누락, 보안과 범위를 살피고 파일을 수정하지 않도록 지시한다. --model로 모델을 고르거나 hooks.reviewCommand로 리뷰 명령을 교체할 수 있다. 리뷰어 실행 기본값과 템플릿 경로
  2. 출력 해석. 프롬프트가 요구하는 소견은 심각도·위치·문제·수정안이다. HIGH 또는 MEDIUM이 있으면 VERDICT: BLOCK, 없으면 VERDICT: CLEAR를 마지막 한 줄에 쓰도록 한다. 구현은 stdout에서 일치한 마지막 판정 줄을 사용한다. 프로세스 종료 코드가 0이고 판정이 있을 때만 PR·SHA·판정·모델·시각·출력 끝부분이 담긴 리뷰 기록(receipt)을 저장한다. 소견의 심각도를 재계산하지는 않는다. 리뷰 프롬프트 판정 파싱과 저장
  3. 병합 결정. dori merge는 PR의 현재 head를 다시 읽어 같은 SHA의 CLEAR 기록을 찾는다. GitHub 체크는 하나 이상 pass이고 나머지가 모두 pass 또는 skipping이어야 한다. 조건을 충족하면 그 SHA를 --match-head-commit에 지정해 squash merge한다. 검토 뒤 새 커밋이 올라오면 새 SHA의 리뷰 기록이 필요하다. 다만 기본 프롬프트가 제시하는 diff 조회 명령은 PR 번호를 사용한다. 기록에는 시작 시점의 SHA가 남지만, 리뷰 도중 PR이 바뀌었을 때 리뷰어가 읽은 diff까지 검증하는 절차는 없다. 병합 조건 리뷰 기록 키

무엇을 같은 일로 볼까대화 키, 입력 이벤트 키, 작업 ID, 시도 번호를 구분한다. 리드는 입력과 작업의 연결을 기록한 뒤 lane을 배정한다. 반응까지 위임한다면 원래 이벤트 키도 전달하는 입력 형식을 마련한다.stdout 출력 직후 강제 종료해 같은 줄이 돌아와도 lane은 하나다. 같은 스레드에서 별도로 요청한 일에는 새 작업 ID가 생긴다.
무엇이 성공인가위임 때 산출물, 실행 가능한 검사, 리드가 읽어볼 사항을 쓴다. 완료 주장은 증거와 함께 보관하고 검증한 시도의 결과만 확정한다. 정리 결과도 별도로 남긴다.예시 파일의 버전이 1이면 실패 사유와 실측값을 남긴다. 2로 고친 시도가 검증되었을 때만 스레드에 완료를 알린다.
누구에게 무엇을 다시 보낼까receipt가 불분명하면 먼저 pane과 기록을 읽는다. 결과가 기준에 미달하면 같은 작업에 관찰값·기대값·다음 검사를 담아 수정 요청을 보낸다. 접근 권한처럼 작업자가 해결할 수 없는 문제는 리드가 맡는다.리뷰 반려와 전달 실패가 같은 재시도 루프에 들어가지 않는다. 이전 시도의 늦은 완료 알림이 새 시도나 사용자 정지를 덮지 않는다.

첫 연결 범위로는 한 Slack 스레드에서 리드가 herdr lane 하나를 열고, 작업자가 보고한 JSON 결과를 리드가 검증한 뒤 같은 스레드에 답하는 흐름이 적당하다. 위 사례의 값 1과 2를 차례로 넣으면 위임·반려·재청구·종료를 한 번에 확인할 수 있다. 당직과 시간별 백로그는 여러 작업을 동시에 관리할 때 추가할 수 있다.
